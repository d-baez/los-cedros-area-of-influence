## Name: Los Cedros - Area of influence Map
### expected outcome:
- Interactive map that outlines the Bosque Los Cedros reserve boundary and highlights the neighboring communities and what they have to offer to visitors. The map should include key landmarks, roads, and points of interest in the surrounding area. It should also provide information on local amenities, such as restaurants, shops, and recreational activities available to visitors. The goal is to create a comprehensive visual representation that helps visitors understand the location and its surroundings, making it easier for them to plan their visit and explore the area.

## project structure
- `index.html` — single-page app; the entire site is this one file plus its asset folders (no build step, no framework). It is a **qgis2web** export (an OpenLayers map generated from QGIS) with hand-added "scrollytelling" styling/markup layered on top.
  - `<head>` — loads OL/qgis2web CSS from `resources/`, then a block of custom CSS for the story layout (masthead header + sticky `.map-pane` / scrolling `.text-pane` split) plus the `.lang-toggle` EN/ES button styling.
  - `<body>`
    - `header.masthead` — the EN/ES language toggle (top-right) plus eyebrow/title/dek text, all filled in by script from `translations[CURRENT_LANG]` (see `data/i18n.js`).
    - `.story` — flex row: `.map-pane` (sticky, holds `#map` + `#popup`) and `.text-pane`. All 4 non-community sections (overview, boundary, station — plus the community sections) have their step-label/heading/body text filled in by script rather than hardcoded, so everything switches with the language toggle. The community sections (`data-step="3.."`) are **generated at load time** into `<div id="community-sections">` from `data/communities.js` — see below.
    - Script tags load `data/i18n.js`, `data/boundary.js`, `data/station.js`, and `data/communities.js` first, then the OL/qgis2web runtime, then the 3 layer data files (all now generated from those data files), then the 3 matching style files, then `layers/layers.js` (assembles the map/layer list), then the Legend/LayerSwitcher setup, then a final inline `<script>` that (a) defines `renderStaticText()`/`renderCommunityText()`/`updateFeaturePopups()`/`setLanguage()` for the language system, (b) builds the community `<section>` elements and `WAYPOINTS` entries from `data/communities.js` (built ONCE — language toggling only updates their text, not the DOM nodes, so scroll position/`IntersectionObserver` are undisturbed), and (c) wires the `IntersectionObserver` on `.section` elements so scrolling a section flies the map to its `WAYPOINTS` entry.
- `data/i18n.js` — **language support.** `translations.en`/`translations.es`: fixed site-chrome copy not tied to a place (masthead, "Legend" button label, overview/boundary/station step-labels & headings). `CURRENT_LANG`: detected once at load (`localStorage` remembered choice > browser language > English), updated by `setLanguage()` in `index.html`. `pickLang(field)`: resolves a bilingual `{ en, es }` object (or a plain string, unchanged) to the current language's text, falling back to whichever language is filled in if one is missing. Every other file that needs to show place content in the right language calls this.
- `data/communities.js` — **single source of truth for all 11 communities surrounding the reserve.** One array of `{ id, name, coordinates: [lon, lat] | null, zoom, duration, shortDescription: {en,es}, description: {en,es} }` objects. Everything community-related is derived from this file at load time instead of being hand-duplicated:
  - `layers/Example_communities_3.js` builds its GeoJSON `FeatureCollection` from `coordinates` (communities with `coordinates: null` are filtered out, so they don't render at `[0,0]`).
  - `index.html`'s inline script builds `WAYPOINTS` (map fly-to targets) and the narrative `<section>` elements from the same array, so the map pins, the scroll-triggered camera moves, and the story text can never drift out of sync again.
  - `shortDescription` (one line, bilingual) feeds the map's click-popup; `description` (full text, bilingual) feeds the scroll-story section — see "two-tier, bilingual descriptions" below.
  - 10 of the 11 communities now have real names (community 11 is still the generic placeholder, commented out); only 4 have confirmed `[lon, lat]` coordinates. The other 7 have `coordinates: null` (marked `// TODO`) — they need real coordinates before they'll appear on the map or in the story. All 11 still have placeholder `description`/`shortDescription` text in both languages. Communities without coordinates are also logged to the browser console (`console.warn`) on page load.
- `data/station.js` — same single-source-of-truth pattern as `data/communities.js`, but for the one scientific station: a single `{ id, name, coordinates, zoom, duration, shortDescription: {en,es}, description: {en,es} }` object. Drives `layers/Scientific_station_SHPScientificStationLocation_2.js`'s FeatureCollection, the station's `<h2>`/`<p>` text in `index.html` (via `#station-heading`/`#station-description`), and its map waypoint — edit only this file to rename/move/redescribe the station. `description`/`shortDescription` hold real, human-written Spanish content about the reserve, with an AI-drafted English translation alongside it (flagged for review — see "missing / flagged items").
- `data/boundary.js` — same pattern again, for the reserve boundary outline: a single `{ id, name, shortDescription: {en,es}, description: {en,es}, coordinates }` object, where `coordinates` is the ordered array of ~172 `[lon, lat]` vertices tracing the outline (formatted a handful per line, not one giant minified blob, so it's at least scannable/diffable by hand — though vertex-level edits normally come from re-exporting QGIS, see `IMPORT.md`). Drives `layers/LosCedros_BoundaryLos_Cedros_boundary_1.js`'s FeatureCollection and the boundary's `<p id="boundary-description">` text in `index.html`. Also has real Spanish content + AI-drafted English translation. The boundary's map waypoint stays a fixed overview shot in `index.html` (not derived from the vertices) since it's meant to frame the whole outline, not any one point on it.

### Two-tier, bilingual descriptions (`shortDescription` vs `description`)
Every data-driven place (community, station, boundary) carries two text
fields, each a bilingual `{ en: "...", es: "..." }` object (`name` stays
a plain, untranslated string):
- `shortDescription` — one line. Resolved via `pickLang()` into the
  GeoJSON `properties.description` that `layers/layers.js`'s
  `fieldAliases`/popup wiring reads, so it's what shows when you **click
  a feature on the map** — and it updates live (not just on page load)
  when the language toggles, since `index.html`'s `updateFeaturePopups()`
  re-sets each already-loaded OL feature's `description` property and
  qgis2web's popup renderer reads `feature.get('description')` fresh on
  every click.
- `description` — the full paragraph(s). Used only by `index.html`'s
  inline script to fill the **scroll-story section** text (via
  `pickLang()`); never sent to the map popup.
- Each `layers/*.js` generator does `pickLang(item.shortDescription) || pickLang(item.description) || null`
  for the popup property, so an empty `shortDescription` still falls back
  to showing the full description in the popup rather than nothing — but
  once `shortDescription` is filled in, use it, since a multi-paragraph
  popup is a bad map UX.
- The communities layer originally had no `description` in its
  `fieldAliases`/`fieldImages`/`fieldLabels` config in `layers/layers.js`
  (unlike station/boundary, which inherited it from the KML export) — had
  to add `'description': ...` to all three of those objects for
  `lyr_Example_communities_3` or the popup text would never render.
- `resources/` — third-party/vendor libraries used by the map: OpenLayers (`ol.js`/`ol.css`), `ol-layerswitcher`, `qgis2web.js`/`qgis2web_expressions.js` (qgis2web runtime glue), `photon-geocoder-autocomplete` (search box), `olms.js` (Mapbox-style loader), `Autolinker.min.js`, `functions.js` (qgis2web helper functions), `fontawesome-all.min.css`, `geojson-layer-helpers.js` (hand-written; shared `buildPointFeatureCollection()` and `buildLineFeatureCollection()` used by any data-driven layer — boundary, station, and communities today, POIs once that data lands), plus assets not currently referenced by `index.html` (see "unreferenced" below).
- `layers/` — one JS file per QGIS layer, each defining an OpenLayers vector source/layer from GeoJSON-like data. **All three are now generated, not hand-authored:**
  - `LosCedros_BoundaryLos_Cedros_boundary_1.js` — the reserve boundary outline. Builds its FeatureCollection from `data/boundary.js` via `buildLineFeatureCollection()` (a single `LineString` feature). Don't hand-edit coordinates/name here; edit `data/boundary.js` instead.
  - `Scientific_station_SHPScientificStationLocation_2.js` — the scientific station point. Builds its FeatureCollection from `data/station.js` via `buildPointFeatureCollection()` (KML-leftover properties like `timestamp`/`tessellate`/`icon` are preserved as constants for compatibility with `layers/layers.js`'s `fieldAliases`). Don't hand-edit coordinates/name here; edit `data/station.js` instead.
  - `Example_communities_3.js` — the neighboring communities. Builds its FeatureCollection from `data/communities.js` via `buildPointFeatureCollection()`. Don't hand-edit coordinates/names here; edit `data/communities.js` instead.
  - `layers.js` — creates the OL `Map`, base layer, and the `LayerSwitcher`/`layersList`, adding the three layers above to it. This is what `WAYPOINTS`-driven `flyTo()` in `index.html` depends on (`map` must exist globally). Untouched by the data-driven restructuring — still hand-authored qgis2web output.
- `styles/` — one JS file per layer defining its OpenLayers style function (matches each `layers/*.js` file by name), plus `styles/legend/*.png` legend swatch images used by the layer switcher/legend UI.
- `images/` — currently **empty**; reserved for the story photos referenced (as commented-out placeholders) in the generated community sections and the fixed sections.
- `scripts/sync-communities-from-geojson.js` — dev tool: patches `data/communities.js` coordinates from a freshly re-exported QGIS communities layer without clobbering hand-written names/descriptions. See `IMPORT.md`. (The station and boundary each have only one feature, so they're updated by hand directly in `data/station.js`/`data/boundary.js` — no script needed; the boundary in particular is a straight vertex-array replacement since a full re-export usually redraws the whole outline.)
- `IMPORT.md` — step-by-step checklist for merging a new QGIS/qgis2web export (boundary/area, scientific station, communities, future POIs, vendor lib updates) into this project without a full export overwriting the hand-customized `index.html`/`data/*.js`.
- `.idea/` — JetBrains IDE project settings (not part of the app), now gitignored.
- `package.json` — placeholder only (`no test specified`); no real dependencies, build, or dev script exists. The site is static and needs no build step (only Node is needed, dev-time only, to run `scripts/sync-communities-from-geojson.js`).
- `README.md` — populated: project overview, quick-start (`python3 -m http.server`), a file map, "how to update the content" instructions pointing at `data/communities.js`/`data/station.js`/`data/boundary.js`/`IMPORT.md`, and a "Language (English/Spanish)" section explaining `data/i18n.js`.
- `.gitignore` — excludes macOS (`.DS_Store`, `._*`) and JetBrains (`.idea/`) cruft, plus a gitignored `qgis-export/` scratch folder for staging raw exports (see `IMPORT.md`).

## how it works end-to-end
1. `index.html` loads `data/i18n.js` (language support), then `data/boundary.js`, `data/station.js`, and `data/communities.js` (the source of truth for all three data-driven layers), then OpenLayers + qgis2web runtime from `resources/`.
2. `layers/*.js` + `styles/*.js` define the three data layers and their styling — each `layers/*.js` file derives its feature(s) from the matching `data/*.js` object/array via `resources/geojson-layer-helpers.js`, resolving bilingual text with `pickLang()`.
3. `layers/layers.js` builds the actual `map` object and adds those layers.
4. The Legend/LayerSwitcher is instantiated and added to `map`, with its tooltip label set from `translations[CURRENT_LANG]`.
5. The final inline script in `index.html` builds `WAYPOINTS` (1 fixed overview + 1 boundary + 1 station + 1 per located community), builds each community `<section>` DOM node ONCE, does the initial `renderStaticText()`/`renderCommunityText()`/`updateFeaturePopups()`/`updateLegendLabel()` render pass, wires the EN/ES toggle buttons to `setLanguage()` (which re-runs all of those), and sets up the `IntersectionObserver` on `.section` elements so scrolling a section flies the map to its `WAYPOINTS` entry.
6. Clicking features on the map presumably opens the `#popup` element (via qgis2web.js's built-in popup logic) with feature attribute info (e.g. Autolinker turns URLs in popups into links) — reading `feature.get('description')` fresh each time, which is why toggling language updates already-open-able popups without a page reload.
